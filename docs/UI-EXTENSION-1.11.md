# UI extension record: native Windows console and shared icons, 1.11

This extension turns the Windows management surface described in [the 1.10 record](UI-EXTENSION-1.10.md) into a dedicated desktop window and repairs management navigation that could leave controls unavailable. The product story stays the same: configure on the PC, operate the live board on the tablet. The first view retains the sidebar, studio overview, connection status, and direct setup/editor actions, now inside the application's own resizable Windows frame.

The incumbent `companion/wwwroot/style.css` remains visual authority: bundled Manrope, charcoal canvas, tonal surfaces, ivory text, secondary text, outline dividers, cyan actions and focus, rounded controls, and existing field/confirmation patterns. This is an ordinary extension, not a replacement visual world. No `PRODUCT.md`, `DESIGN.md`, or design sidecar is created or regenerated by this record.

## Desktop window and lifecycle

`companion/DesktopConsole.cs` hosts the existing `desktop.html` management document in a WinForms window with Microsoft Edge WebView2. It starts centered at 1280 × 860, has a 900 × 620 minimum, supports DPI scaling, and uses the shared application icon and incumbent canvas color. The content fills the frame; this is a native shell around the local web interface rather than a rewrite of its controls as WinForms widgets.

Normal executable launch creates the tray and opens the window. A second launch reads the existing local session and requests the protected `/api/admin/window` endpoint, reusing the running companion. A headless service returns a conflict with restart guidance instead of creating a window. `--no-browser`, `--no-tray`, and explicit tray behavior remain represented in launch policy; self-tests have their own isolated path.

Closing the window through the Windows close control hides it. The tray's **Open Tablet Deck Studio** action and double-click restore the same form and WebView session, including its current document state. A minimized window is restored before activation. Tray **Exit** stops the companion; the console's existing **Stop companion** action retains its unsaved-edit, running-action, held-key, and confirmation guards. Closing to the tray does not stop tablet connections.

The WebView has a persistent profile below the companion data directory. While it starts, a native status label reads **Opening your studio…**. Missing WebView2 Runtime gives an explicit download action while the tablet service remains running. Load/start/process failure messages explain the corresponding reopen or restart action. These fallback states are implemented; the saved test results do not establish their visual appearance.

## Reliable inline management and monitoring

The Windows surface retains its persistent management sidebar, 232px wide at larger sizes and 190px below 1000px, its 84px header, and a flexible scrollable content area. Existing narrower CSS remains in source, although the native window prevents resizing below its 900px minimum. Overview and Board editor have saved wide and small rendered content captures.

Desktop tools use the existing dialog element as an inline, nonmodal destination through `panel.show()`. Tablet tools continue to use `showModal()`. This lets the PC sidebar stay actionable while a management destination is open. Navigation still asks before discarding dirty edits, closes monitoring when opening a tool, and retains the editor area when switching tools. The panel close event returns to overview only if the panel is actually closed, avoiding a late close event hiding a newly opened destination. **Back** closes the inline destination.

`monitor.js` now wraps the default timer calls in functions instead of passing unbound browser `setTimeout` / `clearTimeout` methods into the preview controller. Saved rendered checks exercise preview start/stop without timer invocation errors, then return to the editor without blocked clicks. They do not demonstrate real OBS capture. The 1.10 preview, public-chat, consent, cancellation, and Android separation boundaries remain applicable.

Desktop input and textarea placeholders now explicitly use the existing secondary text token at full opacity. This addresses the placeholder contrast defect found in the first review without adding a palette value. Both recaptured editor views show secondary text (`#b8c3d1`) against the field background (`#131922`), approximately 9.89:1 contrast. The final reviewer returned **ship**, scoped to this one placeholder fix, and found no regression from the rule. Labels, status text, sidebar `aria-current`, preview/provider pressed states, and the incumbent cyan keyboard-focus outline remain in place. Full assistive-technology and keyboard interaction approval has not been established by the saved checks.

## Native host boundaries

The native host exposes no host-object or web-message bridge, denies WebView permission requests, and disables developer tools, default script dialogs, and the status bar. Its top-level navigation permits only HTTP `127.0.0.1` at the expected companion port with the `/desktop.html` path and no URL credentials. Other top-level navigation is cancelled. User-initiated external navigation and new windows can open through Windows only for credential-free HTTPS DNS hosts on port 443 that are not loopback.

Downloads reach a native Save dialog only for the expected local origin or its blob URLs; other downloads are cancelled. The chooser supports board JSON/deckpack files and asks before overwriting. These rules concern the native host and top-level document; remote public chat remains governed by the existing iframe/CSP or separate Android chat-view policy.

The window-opening endpoint uses the existing local admin checks: loopback connection on the admin port, session header, host/origin restrictions, and cross-site request rejection. No new unauthenticated window-control route is introduced. Saved checks cover a missing admin credential and refusal by a headless service, plus the native URL/export predicates.

## Shared application mark

`assets/app-icon.svg` is a minimal four-key mark: three cyan rounded squares and one ivory square on the existing charcoal rounded field. It reuses the incumbent canvas, cyan, and ink colors. `scripts/Build-Icons.ps1` reads that SVG to generate the PNG preview and seven-frame Windows ICO (16, 24, 32, 48, 64, 128, and 256px), and copies the SVG into the console assets. The console uses it as its favicon and decorative sidebar mark; the executable embeds the ICO, and `AppIcon.cs` supplies it to both window and tray.

Android uses the same four-key motif in its foreground vector, charcoal adaptive background, and Android 13 monochrome vector. Versioned adaptive launcher resources select the monochrome layer where supported, and the manifest points to the launcher resource. Windows installer shortcuts target the companion executable and its embedded icon, with the desktop-app description. This records matching source assets and resource wiring; it is not physical Android launcher/mask or Windows shell icon-cache approval.
