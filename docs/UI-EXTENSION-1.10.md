# UI extension record: Windows console and monitoring, 1.10

This extension adds a dedicated Windows management console, optional local OBS preview, and editable Twitch/Kick public chat viewers to the incumbent Studio / Operate world described in [the 1.9 extension record](UI-EXTENSION-1.9.md). It responds to the request for a PC interface distinct from the tablet action board. The tablet keeps its live board; the PC has a sidebar, overview, and inline management editor. The 1.9 statement that video/chat are later roadmap work is superseded by the implementation described here, subject to the verification limits below.

`companion/wwwroot/style.css`, its existing dark canvas/surface layers, outline dividers, ink/secondary hierarchy, cyan action/focus treatment, bundled Manrope, fields, buttons, and confirmation patterns remain authoritative. This is a scoped extension record. It introduces no new visual identity or token values and does not regenerate `PRODUCT.md`, `DESIGN.md`, or the design sidecar.

## Windows and tablet destinations

`desktop.html` is the Windows console. Its persistent sidebar groups Overview, Board editor, Tablet connections, OBS setup, Soundpad library, Profiles, Backups, OBS mixer setup, Automatic profiles, Portable packs, Monitoring, App volumes, More tools, and Windows options. The header retains OBS connection and stream status. Overview shows the active profile, OBS state, physical LAN address, saved tablet pairing count, active fast-link count, and USB helper status, with direct connection/editor actions and explicit refresh.

Management destinations reuse the existing editors and tools in the main content area. The PC panel is an inline, nonmodal destination with a Back control; it does not require a hidden tablet pad or action grid. Board rendering and tablet fader updates return early on this surface. The tablet's `index.html` remains the Studio / Full pad action board with an optional Monitor destination. Native assets allow only that board's approved local files; the Windows console HTML, stylesheet, and script are excluded from the native asset allowlist.

The desktop shell uses a 232px sidebar and an 84px header, with a flexible content track and a separate running-action row. Sidebar width reduces at 1000px and 620px. The overview and inline panel scroll within their content area. Monitoring uses separate video/chat columns on wider PC layouts and stacks them below 1000px. Video-only and chat-only modes explicitly use one flexible content track. On the tablet, monitoring replaces the mixer beside the keys; the 760px rules put monitoring above the keys, preserving the board destination. Provider tabs and chat actions occupy separate rows to reduce crowding. These are source-level layout provisions, not rendered-fit approval.

Sidebar navigation participates in unsaved-change protection. Monitoring refuses to open while changes are dirty or arrangement is active. Opening another management destination closes monitoring. Closing the inline panel returns to the overview. Generation checks and the existing panel ownership rules continue to protect editor results from late responses.

A normal user launch of the Windows executable can open the console for an already-running companion without starting a second service. `--no-browser` and self-test/headless paths retain their no-GUI behavior. This is launch behavior in the new source, not evidence that an older running process has acquired the new interface.

The sidebar footer provides **Stop companion**. Unsaved edits, busy/running actions, and held keys block it before confirmation. The confirmation explains that tablet controls and deck sounds stop while OBS streaming and recording continue. Declining leaves the service running; confirming uses the protected shutdown endpoint and gives restart guidance.

## Local OBS preview

Opening Monitoring does not capture video. **Start preview** explicitly requests the selected OBS scene as low-frame-rate JPEG images with no audio. Settings offer Program output or Studio preview scene, widths of 320/640/960px, maximum rates of 1/2/4 frames per second, and Video + chat / Video only / Chat only layouts. Defaults are Program, 640px, 2fps, and both panes. Settings persist on the current device; saving settings alone does not automatically begin capture.

The interface labels the output as a silent, low-frame-rate preview and displays elapsed time since the last received frame, marking it stale after three seconds. **Pause preview** stops polling while retaining the last image. Closing monitoring stops polling, clears the image source, and resets the requested video/chat state. A decode failure hides the image and directs the user to start again. Hidden/background state, a tool panel, or confirmation pauses monitoring; resuming restores only an activity the user had requested. Late or superseded requests cannot render into a stopped or replacement session.

Preview uses a separate OBS client rather than the control connection. Android routes frame requests through its separate single-worker preview executor. The browser loop permits one in-flight request and schedules no replay queue; failures back off. The companion shares a matching recent frame for less than 250ms and enforces a global 250ms capture-attempt interval across sizes and modes, a four-frame-per-second ceiling. Busy capture is rejected instead of queued. Capture respects cancellation and a four-second deadline, and releases its gate afterward.

Capture reads the current program or actual Studio preview scene and OBS canvas dimensions without changing scenes or starting outputs. Missing Studio preview gives enable/scene guidance. The service requests JPEG quality 55, preserves the canvas aspect ratio, bounds requested size and resulting dimensions, rejects unsupported canvas values, and validates the JPEG format, base64 data, decoded size (384KB maximum), and dimensions (8–1280px per axis). These controls bound preview work; they do not establish full-motion performance or a latency guarantee.

## Editable public chat viewers

Monitor settings start with empty, editable **Twitch channel** and **Kick channel** fields. Names are trimmed, normalized to lowercase, and may lose a leading `@`; URLs and unsupported characters are rejected. The current provider and settings are saved locally. The form has normal dirty/save/error behavior and explains that loading chat contacts the selected provider. No streaming-account password is stored by this feature, and the application does not automatically post chat messages.

Selecting Twitch/Kick chooses the public viewer. **Load chat** is explicit and requires a configured channel; opening monitoring or saving fields does not contact a provider. **Unload chat** removes the requested viewer. On the PC, the provider loads in a titled, sandboxed iframe, with Twitch's parent parameter derived from the actual console hostname. **Open chat window** is an explicit public-popout fallback. The text explains that provider cookies, sign-in, challenges, embedding restrictions, and Internet access can affect availability; successful frame loading is not proof that chat is usable.

On Android, public chat is a separate WebView positioned within the requested monitor bounds. It has no `DeckNative` JavaScript bridge. The privileged board document retains its local asset allowlist, `frame-src 'none'`, and blocked network access; remote chat is never embedded into it. The separate viewer permits only HTTPS resources for the selected provider and its enumerated supporting domains, with main-frame navigation constrained to the selected channel's public chat path. Local/loopback URLs, arbitrary providers, credentials in URLs, nonstandard ports, file/content access, mixed content, downloads, and external intents are blocked. Certificate failures are cancelled. Provider challenges are allowed only through the stated resource policy, without bypassing them.

Hiding chat destroys its WebView rather than merely covering it. Closing monitoring, opening tools/confirmations, or backgrounding removes the remote surface. Native pause also destroys it; resume can recreate only the previously requested viewer. Session checks suppress late callbacks, and bounded layout requests reject areas outside the board or too small to use. These are source and policy boundaries, not a claim that every provider's current page will function within them.

## Connection guidance and current hardware state

The PC refreshes connection summary data every five seconds while visible and outside an editor, and supports **Refresh status**. Physical LAN addresses precede virtual-adapter alternatives. Saved pairing records are distinct from active persistent fast links; the connection data also exposes per-device fast-link and last-seen information without exposing pairing credentials. A saved pairing or recent authenticated request is not proof of a current fast connection. The overview directs users to the tablet for its actual Wi-Fi/USB transport status.

Guidance explicitly supports an Ethernet PC and Wi-Fi tablet on the same local network. It calls for the physical LAN address, a running companion, and both local control ports. USB guidance retains debugging authorization, both tunnels, and the complete package's bundled platform-tools folder. Switching transport retains pairing rather than demanding a fresh trust exchange.

Hardware investigation reported both USB ports 8743/8744 reachable after tunnels were restored. Wi-Fi testing used PC Ethernet address `192.168.1.21` and tablet Wi-Fi address `192.168.1.20` on the same subnet, but TCP attempts timed out. The user ran the bounded administrator firewall helper. This does not establish that the firewall was the sole cause or that Wi-Fi is fixed.

The tablet initially had version 1.5.1 and temporarily disappeared from PnP, ADB and mDNS. Parent-agent follow-up after this documentation pass: it returned authorized, APK update succeeded and Android metadata confirmed1.10.0/code13. The companion was updated headlessly at its existing path; board, pairing, certificate and Windows preference file hashes were unchanged. Fresh tablet-side TCP probes passed for USB127.0.0.1:8743/8744 and LAN192.168.1.21:8743/8744. These verify installation and network reachability, separately from authenticated app controls or rendered monitoring. See LIVE-TEST.md for the dated follow-up.
